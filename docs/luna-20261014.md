## TB2 为什么没有优化出增益

这里的“没复现成功”指 **迁移到 Luna / TB2 后没有得到超过 seed 的返回版本**。三个上游优化器都执行并完成了自己的循环；返回 seed 是其接受与选择规则的实际结果，并非没有调用优化器。但验证分数受到环境问题污染，因此不能把结果解释成优化方法本身无效。

### “没有新 final skill”不等于“没有 optimizer work”

TB2 的持久化产物明确显示，三个优化器都生成过候选、执行过 rollout，并把候选送入选择阶段：

- SkillOpt 的 `history.json` 有 5 个 step；每个 step 都有候选 skill、selection 评估和 `action=reject`。候选分数为 5/9、5/9、5/9、5/9、6/9，seed 为 6/9，所以 `best_step=0`、`best_origin=initial_skill`。
- SkillAdam 的 checkpoint 有 18 个 iteration，`iterations/` 中有 21 份 patch JSON 与 21 份 exchange JSON（共 42 个文件，并非 42 次 patch）；候选不是都为空。10 轮候选为 5/9，8 轮为 6/9，但 0 轮通过严格 gate，最终 `current_skill` 和 `final_skill` 都回到 seed。
- GEPA 的 `run_log.json` 有完整 20 轮，候选池有 seed 加 4 个子代；4 个子代的完整 D_sel 分数为 5/9、5/9、6/9、5/9。日志里的 `accepted=4` 只表示子代进入候选池，最佳分数与 seed 持平时按候选索引保留 seed。

因此，TB2 观察到的是 **proposal / patch / evaluation 都发生了，但没有候选形成严格的 best improvement，所以没有新 final skill 被发布**。这是上游优化器的 native selection behavior：SkillOpt 比较 `candidate_score > current_score`；SkillAdam 的默认 `AcceptanceGate` 要求 `primary` 严格增加；GEPA 选择完整验证集的最高分，平分时保留先出现的 seed。它是 elitist、单调的发布规则，不是“策略性地不生成 skill”。

续跑后的 `summary.json` 不能单独用来判断是否做过 work：SkillOpt 的 `token_summary` 只反映最后一次进程的计数，可能是零；训练侧的 `executed=0` 也可能只是复用了 seed cache。判断应以 `history`、iteration/patch 文件、候选文本和逐轮 evaluation 为准。这里没有修改历史 summary 或 checkpoint。

### 1. 三个优化器实际发生了什么

三个方法的固定 D_sel 都只有 9 题，seed 的记录分数为 **6/9**。一题就改变 11.1 个百分点；SkillOpt / SkillAdam 要求严格提高，GEPA 最终选验证集最高分，平分时保留索引较早的 seed。

| 优化器 | 已提交循环记录 | 为什么返回 seed |
|---|---|---|
| SkillOpt | 5 个候选；第 1–4 轮为 5/9，第 5 轮为 6/9；5 次 reject | 没有候选超过 6/9，`best_step=0`、`best_origin=initial_skill` |
| SkillAdam | 18 轮；10 轮为 5/9，8 轮为 6/9；0 次接受 | 全部触发 `no metric exceeded its strict improvement threshold`。第 7、12、16 轮为空 patch，候选实际等于 seed；其余 15 轮确实改变了文本 |
| GEPA | 20 轮：15 次 minibatch reject、4 个子代进入候选池、1 次 reflection failure | 四个子代完整 D_sel 分数依次是 5/9、5/9、6/9、5/9；最佳仍为索引 0 的 seed。第 14 轮是 `APIConnectionError` / `Server disconnected without sending a response`，上游跳过该轮 |

不能把 GEPA 的 `accepted=4` 解读成最终有四次验证提升：那是训练 minibatch 的入池接受。也不能从某次续跑 summary 中空的 LLM 计数断言 SkillOpt 没做提案，持久化 history 与候选文本证明它做了五轮。

### 2. 两道固定失败题实际是 verifier 环境问题

seed 在 D_sel 失败的是 `qemu-alpine-ssh`、`qemu-startup`、`raman-fitting`。所有查到的完整 9 题 dev evaluation 都没有修复这三题；大量候选还新增 `query-optimize` 失败。继续读 verifier 原始日志后，不能把前三题一律视为模型能力不足：

| 任务 | 原始证据 | 对结论的影响 |
|---|---|---|
| `qemu-alpine-ssh` | Debian bullseye-security 的 `libnghttp2` / `libcurl4` / `curl` 下载 404；随后 `curl: command not found`、`uvx: command not found`。seed 另有 agent 900 秒超时 | verifier 本身没有正常执行；历史 reward=0 / `task_verdict` 不能当作干净的能力测量。agent 超时与 verifier 失败同时存在 |
| `qemu-startup` | 同样的 apt 404 和缺失 `curl` / `uvx`；最终 reward=0，backend 却分类为 `task_failure` | 明确的基础设施失败被当成训练/选择负反馈 |
| `raman-fitting` | verifier 正常断言失败：seed 的 G 峰 x0=19196.4，期望 1580.3；2D 峰 x0=16207.93，期望 2670.08 | 有实质性的拟合结果错误，仍有待改善的任务能力；没有候选将此题变为成功 |
| `query-optimize` | seed 成功；查到的 20 个失败 evaluation 均失败在 SQL 性能测试。一个 SkillOpt 候选输出正确，但中位耗时 1.340s，大于 `1.05 × 0.968s` | 这次许多 6/9→5/9 的退化来自性能门槛，不是 SQL 输出错误；单次执行不能进一步区分编辑影响与运行波动 |

检查范围为 Seed、SkillOpt、SkillAdam、GEPA 的 **32 个完整 dev evaluation 文件**，包含基线复用和续跑残留，并不等于 32 个已提交候选。它们的 64 个 QEMU 槽位映射到 **58 份不同的 `verifier/test-stdout.txt`**；58 份都有 apt 404 和 `uvx` 缺失。上表的 20 个 SQL 失败 evaluation 同样包括未提交尝试，不应混入逐轮接受统计。

因此，比“seed 太强”更有证据的解释是：**验证集很小，其中两题持续给出受环境污染的零分；真实失败题没有改善，候选又容易损失 SQL 性能题；严格提高 / 最佳返回规则最终留下 seed。** 严格 gate 解释了为什么平分候选不被选中，但不是这批失败的唯一原因。这里没有事后删除两题、修改 Q，或放松 gate 来制造提升。

## 调度与审计问题为什么会出现

1. **训练与重复测试分散在两套入口。** 旧 BACH `composition/gpt-6-luna/baseline.sh` 只调度三个优化器的 native run，再调 Seed / No-skill 的重复测试，没有三个优化器的 repeat job。另有 `replicate.py` 只列旧 DeepSeek gains，无法覆盖 Luna；`test_reps.py` 遇到最终 skill 等于 seed 就直接返回，并未检查 Seed 真有三次结果。没有完整的启动日志证据能说明 Seed / No-skill 的重复任务为何没执行，所以这里确认的是调度设计缺口及产物缺失，不推断某次后台进程具体如何退出。

2. **审计器仍写死十轮。** `audit_native_run.py` 原来要求 SkillOpt / GEPA 的冻结 batches 必须恰好为 10。真实 full-train 的 τ³ / AutoB 是 SkillOpt 4、GEPA 20、SkillAdam 16 轮；TB2 为 5 / 20 / 18。对配置内的正常轮数报错是审计缺陷。现在改成逐项验证冻结 schedule，不改变实验预算。

3. **空响应表示差异造成附加误报，但捕获不完整是真的。** harness-bench 的 `src/eval/worker.py:normalize_calls` 将原始 `response=None` 通过 `_mapping()` 写成 `{}`；旧审计直接比较两者，产生 `request_source_payload_mismatch`。本地审计现在只把 None 和空 dict 视为同样缺失的响应，仍单独要求完整捕获，不能凭此获得认证。

   抽查 GEPA τ³ 的 `results/evaluations/dev/0572e6dec280-ee50f063be15/evaluation.json`，任务 `tau3-airline-1` 的 request index 13（记录 ID `request:5cfcffc039981ff380af547d`）原始请求与导出请求相同，但响应为 None / 空 dict。原始 transport 还记录 `ConnectionResetError`，`response_end.complete=false`、`reason=transport_error`，usage 缺失。原始流保留 error / response.failed 内容，没有正常完成响应。该任务总共被捕获器标记 8 次不完整调用，工具账本还有 11 个 dispatch ID 无法与归一化响应中的调用闭合。因此请求成本和调用图仍不能视为完整；本地整理不修改外部捕获实现，也不补造 tokens 或工具响应。

4. **GEPA 的文本日志跨续跑追加，JSON checkpoint 只保留提交轮次。** τ³ 第 12 轮有两次 `Selected program`，第一次 parent=3，恢复后提交的 JSON 记录 parent=2、new_program_idx=6；旧解析器只要同轮标题多于一个就放弃生成状态。AutoB 也有两轮相同问题。现在只在 parent 与明确提交标记唯一匹配时解析，多个已提交候选仍保留歧义，不盲选最后一段。只读解析已确认三个 GEPA benchmark 均可定位全部 20 个已提交轮次；历史 round-state 文件和证书未重新生成。

5. **逐轮见证引用了可变的有效 evaluation。** 三个 GEPA run 各有两条 `round_evaluation_file_missing_or_changed`。抽查 τ³ 是 step 12 的 full_selection、step 13 的 minibatch；对应 evaluation 记录了 unknown-only 追加重试和替换 lineage。旧 round event 先冻结了这个可变文件的哈希，重试后文件改变。新记录逻辑保存按内容哈希寻址的不可变 evaluation 快照，并另外记录有效文件位置；审计仍检查快照的真实请求证据。无法从旧哈希恢复旧文件，因此不回填历史快照。

6. **summary 的原语义过宽。** 原 `require_complete` 只检查行数，并允许未知结局，所以 summary 存在只说明优化结束，并不表示全部任务、全部重复或完整成本已知。现在检查 task ID / repetition 的精确覆盖，单次 summary 增加 `outcomes_complete`，重复评测必须检查所有请求重复。TB2 的第 18 个 unknown 不会被强制当失败，也不会为了补齐而自动重新抽样。

其他历史失败（如 TB2 的未解析物理证据、skill 交付见证和 backend outcome 不一致）仍保留；这里没有声称所有错误都由上述两个误报解释，也未做九格全量重新认证。另需留意既有 `bipa/analysis/luna_table.py`（2026-10 自 `bach-harness/src/analysis/` 迁入）只累计有 input_tokens 的请求，部分调用状态按“不是 false”计数；这类子集汇总不能作为完整 episode 成本认证。本次未重算或替换其论文产物。
